## User Perspective — Improvement Suggestions

**What the user asked, directed, corrected, and how they did it.**

### Observation: Hyper-concise direction style
The user communicates in 1-5 word directives: "green light", "closeout then start X",
"run the historian", "proceed with auto implementation of approved lugs". Zero waste.
This is a consistent, stable preference — not a session artifact.

**Implication:** When the agent produces long preambles before acting, it's mismatched.
The user wants action, not narration. Brief status line then execute.

### Observation: High-trust delegation on execution
Once Green Light is given, the user does not re-enter to verify steps. They come back
for the next directive. The "challenge + value" ask (taste-collab-001) was a correction
to make GREEN LIGHT ASKs informative — not a request for more check-ins during execution.

### Observation: Task-chaining preference
Sessions 26-27 show chaining: "closeout then start X", "green light" (next message).
The user thinks in flows, not atomic tasks. They expect the agent to do the full chain
(closeout + new session + epic + dogfood + ask for Green Light) without stopping.

### Observation: No frustration signals in 45 points
Zero instances of the user repeating themselves, saying "no", or correcting fundamentals.
This is either a sign of alignment or a sign that friction is being swallowed without
surfacing. The deferred open threads (see Model section) suggest the latter.

**Nudge proposal (taste.spoke):**
> Category: communication
> "Minimize narration before action. When executing a known plan or Green Light task,
> start with a 1-line status ('Executing epic-X now.') then act. Reserve prose for
> genuinely new decisions or unexpected findings."

## Model Perspective — Improvement Suggestions

**What the agent did, how it reasoned, where it struggled.**

### Finding: Decisions array is polluted with session metadata
Almost every session records "Session ID: session-XXXX" or "Previous session: clean
closeout, no recovery needed" as decisions. These are not decisions — they are log
entries. The decisions field is supposed to capture "choices made this turn" that
affect future behavior. Recording session IDs degrades the decisions field and makes
pattern-scan's reopened_decision detection less useful.

**Affected sessions:** track_20260314-0903, 0925, 0959, 1012, 0029, 0151, 0506, 0527
(8 of 12 sessions)

**Nudge proposal (taste.spoke):**
> Category: workflow
> "In the track point decisions[] array: only record architectural or technical choices
> that affect future behavior (e.g., 'Store artifact in reference/, not spoke root').
> Do NOT record: session IDs, 'previous session clean closeout', 'new session: X'.
> Those are log entries, not decisions."

### Finding: Unresolved open thread — epic-track-system-install-and-cleanup-v1
The "legacy WAI-Spoke root cleanup" sub-task appeared in open[] for 5 consecutive
sessions (0903 → 0029, spanning March 14). It was in-progress but never appeared
as resolved in any tracked closeout. The epic was later closed (epic status shows 'c')
but the specific legacy cleanup disposition is unclear.

**Investigation prompt:** Was the WAI-Spoke root legacy cleanup actually completed, or
was it silently dropped when the epic was closed? Check epic closeout record and WAI-Spoke
root for leftover legacy files.

### Finding: Pattern-scan flags routine operations as workaround_churn
The pattern-scan (run as part of this review) found 40 clusters, but ~30 are normal
protocol operations: reading WAI-State.json, reading WAI-Lugs.jsonl, writing track
points, running git status, bumping versions. These appear in every session by design.
Flagging them as "workaround_churn" is noise.

**Calibration needed:** The pattern-scan activity[] comparison needs a filter for known
protocol operations. Suggested filter list:
- "read WAI-State.json", "read WAI-Lugs.jsonl", "ran git status", "wrote track point",
  "wrote final track point", "appended session-summary", "bumped version", "ran wakeup",
  "ran closeout", "updated _session_state", "parsed WAI-Lugs.jsonl"

Pattern_type workaround_churn on activity[] is only meaningful for non-protocol actions.

### Finding: Short sessions dominated by wakeup overhead
Sessions track_20260313-0730 (2 turns, review only) and track_20260313-1845 (1 turn,
orientation only) accomplished almost nothing. The wakeup protocol reads multiple files
and produces a full briefing — in a 1-2 turn session, this is the entire context cost.
Not a problem per se, but notable: the ratio of wakeup overhead to productive work is
high for very short sessions.

## Directions Perspective — Improvement Suggestions

**Specs, prompts, skills, protocols — gaps, strengths, ignored rules.**

### Finding: 3-file wai.md sync is a maintained friction cost
templates/commands/wai.md, .claude/commands/wai.md, and templates/spoke/commands/wai.md
are kept in sync manually. Every protocol change to Step 5c (and Steps 5a, 6, 9 already
required this) needs 3 edits plus a copy. The activity log shows "synced templates/spoke",
"copied to templates/spoke/commands/wai.md", "updated .claude/commands/wai.md" appearing
in 7 of 12 sessions.

**Not a blocking problem** — the pattern is established and documented. But it's the
single highest-frequency maintenance activity in the track history. Worth noting as a
candidate for a future "single-source wai.md" architecture discussion.

### Finding: next_session_recommendation doesn't create urgency
epic-sessions-flat-storage-v1 sat with Green Light given for 3 sessions before executing
(open[] in 0959, 0151, 0506 — then finally executed in 0527). The next_session_recommendation
field in WAI-State.json listed it as PRIORITY 1 in all three sessions. But the wakeup
briefing presents it as a text note, not a distinct action item.

The current wakeup format shows "Next Actions" derived from lug data — but the
next_session_recommendation string is separate. If a Green Light is given on an epic,
that epic should appear in the wakeup Active Work section with a marker (e.g., status='gl'
or priority='green_lit') rather than just in the state string.

### Finding: Pattern-scan protocol operation filter is missing from skill
The historian.yaml pattern_scan section doesn't specify a filter for routine protocol
operations. This is the calibration gap identified above. Should be added as a
`activity_filter_exclude` list in the pattern_scan section.

### Strength: Teaching protocol is working
The teaching ceremony (mailroom rule, verification summary, explicit approval) is being
followed consistently. Sessions 0925 (5 hub teachings processed) and 0506 (7 hub teachings
processed) show the protocol executing cleanly. No teaching was auto-applied without
presentation.

### Strength: Dogfood gate is catching real issues
The dogfood subagent found real gaps in two sessions (0925: field count wrong; 0029: 3
gaps found in epic). The gate is doing its job. The improvement (full JSON to dogfood
agent vs. prompt summary) was identified and noted.

## Calibration Notes for Pattern-Scan

The first production run of pattern-scan reveals a calibration gap:
the `activity[]` field Jaccard comparison at threshold 0.3 flags every normal protocol
operation as workaround_churn because they recur in every session by design.

**Recommended addition to historian.yaml pattern_scan section:**
```yaml
activity_filter_exclude:
  - "read WAI-State.json"
  - "read WAI-Lugs.jsonl"
  - "ran git status"
  - "wrote track point"
  - "wrote final track point"
  - "appended session-summary"
  - "bumped version"
  - "updated _session_state"
  - "parsed WAI-Lugs.jsonl"
  - "updated WAI-State.json"
  - "git commit"
  - "git push"
```

Items matching any filter string (substring match) should be excluded from
workaround_churn clustering. The open[] and decisions[] fields do not need this
filter since they don't contain protocol operations.
